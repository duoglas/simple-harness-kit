# Evidence Attestation

SHK verification evidence can be bound to the repository state and checked independently before it is used as a delivery or admission signal.

## What `shk verify --write-evidence` records

The structured evidence contains:

- `run_id`: unique identity for the verification run;
- `provenance.git.commit`: `HEAD` at evidence generation time;
- `provenance.git.tree`: the committed Git tree for that `HEAD`;
- `provenance.git.dirty`: whether tracked or untracked worktree changes existed;
- `provenance.mode`: `full`, `incremental`, or `seal`;
- `attestation.issuer` and `attestation.trust_level`;
- `attestation.digest`: SHA-256 over canonical JSON for the entire evidence object except the digest field itself.

The digest detects generation-time evidence that was later rewritten without a new attestation. A `local-self` issuer can still change the evidence and issue a new local attestation, so the digest does **not** resist a malicious local generator or prove that the process was independent. Evidence generated by the local SHK CLI is therefore labeled `local-self`; it must not be described as CI-signed or independently verified.

## Verify evidence

```bash
node scripts/shk.js evidence verify --current-git --require-clean --require-mode full
node scripts/shk.js evidence verify --file path/to/verify-evidence.json --min-trust local-self --format json
```

Useful policies:

- `--current-git`: compare evidence commit and tree with the current repository;
- `--expected-commit <sha>` / `--expected-tree <sha>`: compare with an explicit candidate identity;
- `--require-clean`: reject evidence generated from a dirty or unknown worktree;
- `--require-mode full|incremental|seal`: require an execution mode;
- `--min-trust local-self|local-controller|ci-signed|independent`: require a minimum **authenticated** trust level;
- `--allow-legacy`: explicitly allow evidence without attestation;
- `--format json`: emit structured checks and failure codes.

Without `--allow-legacy`, `shk evidence verify` fails closed when attestation is missing. `--allow-legacy` bypasses only the attestation requirement: commit/tree, clean, mode, and minimum-trust policies still apply, and legacy evidence cannot satisfy a minimum trust level. Missing, duplicated, or unknown verifier options are rejected instead of being silently ignored. Existing SHK hooks preserve legacy evidence compatibility only when evidence has no attestation and strict policy is disabled. If attestation exists, or strict policy is enabled, invalid evidence and an unavailable verifier both fail closed. Projects can opt into strict consumer behavior with:

```json
{
  "evidence": {
    "require_attestation": true
  }
}
```

## Trust boundary

Trust levels describe how evidence was issued; they are not interchangeable:

1. `local-self`: generated and consumed in the same local trust boundary;
2. `local-controller`: generated by a separate local controller;
3. `ci-signed`: generated by an authenticated CI identity;
4. `independent`: produced or confirmed by an independent verifier.

The current SHK CLI only issues and authenticates `local-self`. Merely editing `trust_level` to `ci-signed` and recomputing the digest returns `EVIDENCE_TRUST_UNVERIFIED`; the CLI deliberately exposes no option to bless that declaration. Higher levels require a project or CI integration that first validates a signature/controller boundary and then calls the library verifier with `authenticated_trust_level`. A hash proves consistency, not independent authenticity.

The attestation format also fixes `protected_scope` to `entire-evidence-except-attestation.digest`. Changing the scope and recomputing the digest is rejected as an unsupported attestation format.
